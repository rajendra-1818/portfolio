Things Still to Learn
Part One · Amazon

When I joined Amazon as a Software Development Engineer in 2022, I thought I knew what building software meant. I had a CS degree, a decent GPA, and a head full of data structures. What I didn't have was any real sense of what it meant to write code that millions of people depend on — code where a bad deploy at 2am isn't a learning experience, it's a production incident.

My first few months at Amazon were humbling in the best possible way. The systems were massive. The codebase was old in some places and aggressively modern in others. And the expectations around reliability, observability, and ownership were unlike anything I'd seen in academic projects or internships.

"You don't really understand distributed systems until you've been paged for one at midnight. Then you understand them very quickly."

I was working on backend microservices deployed on AWS — EC2, S3, Lambda — and the work was genuinely exciting. I was writing RESTful APIs, integrating cloud-native services, and learning what fault tolerance actually looks like in practice versus in a textbook. CloudWatch became my best friend. Logs became my primary language.

The thing nobody tells you about AWS at scale

Everyone talks about how powerful AWS is. What they don't talk about as much is how easy it is to build something fragile on top of it if you're not deliberate. Lambda functions that time out under load. EC2 configurations that work fine in staging and collapse in production. I learned that cloud efficiency isn't automatic — it's something you architect for, test for, and constantly revisit.

// What "fault tolerant" actually meant in practice @Retryable(value = {ServiceException.class}, maxAttempts = 3) public ResponseEntity<PatientData> fetchWithFallback(String id) { try { return downstreamClient.fetch(id); } catch (ServiceException e) { log.warn("Downstream failure, attempt logged to CloudWatch"); throw e; // let @Retryable handle it } }

It was also at Amazon where I first understood what it means to own a service — not just write it. You write it, you deploy it, you monitor it, you get paged for it. That ownership mindset changed how I approach every line of code I write.

Part Two · DaVita

When the Stakes Are Human

I joined DaVita in August 2023, and the shift was immediate. At Amazon, a bug might slow down a checkout flow or delay a package notification. At DaVita — a company that provides kidney dialysis to hundreds of thousands of patients — a broken system means something different. It means a missed communication. A delayed report. A clinical workflow that grinds to a halt.

That weight is not a bad thing. It sharpens you.

My first major project was one of the most technically dense things I'd worked on: migrating a suite of enterprise microservices from Java 11 to 21 and Spring Boot 2.x to 3.x. On paper, it sounds like a routine upgrade. In practice, it meant combing through years of accumulated technical debt, undocumented dependencies, and framework-level breaking changes that nobody had bothered to write down.

The Hard Part

Migrating six production services across two major Java versions isn't a weekend project. It's a negotiation — with the codebase, with the framework, with your own assumptions about how things work.

What made it manageable was treating it like an investigation rather than a task list. Every compile error was a clue. Every deprecated API was a breadcrumb. By the time we were done, the services were leaner, startup latency was down, and the team had documentation that actually reflected reality.

Building things that talk to patients

One of the projects I'm most proud of at DaVita was building a real-time patient messaging system using Infobip APIs and QR-based routing. Before this, patient communications ran on overnight batch cycles — meaning a change made at 9am wouldn't reach a patient until the following morning at the earliest. We replaced that with a live pipeline. It sounds like a backend problem. But on the other side of it is a patient who gets their appointment reminder when it actually matters.

I also built automated PDF generation modules integrated with Cloud CMS, and wired up Tableau APIs so operations teams could pull their own analytics without waiting on an engineering ticket. These weren't glamorous features. But they were the kind of work that makes the rest of the organization move faster — and that's always been the work I find most satisfying.

Part Three · The AI Shift

The Tool That Changed My Workflow

Somewhere in the middle of the DaVita migration work, I started using AI tools seriously — not as a novelty, but as a genuine part of how I work. And it changed things in ways I didn't fully anticipate.

The obvious benefit is speed. Tracing a Kafka consumer failure that used to take an hour of log spelunking now takes minutes when you can describe the symptoms clearly and iterate on hypotheses fast. Spring Boot upgrade errors that required digging through changelogs and Stack Overflow threads now resolve in a single well-framed conversation.

But the less obvious shift is cognitive. AI tools reward clarity. The better you can articulate a problem — the constraints, the context, the expected behavior — the better the output you get. And that feedback loop has made me a more deliberate engineer. I write clearer design docs now. I think through interfaces more carefully upfront. I've started treating vagueness in my own thinking as a problem to fix, not a detail to defer.

The engineer who uses AI well isn't the one who types the least. It's the one who thinks the clearest.

I've also changed how I look at repetitive work. If a task is well-defined enough that I can describe it precisely, I start asking whether I should be doing it manually at all. That question — "is this automatable?" — used to feel like a luxury. Now it feels like a professional obligation.

Lessons

What I'd Tell Myself at Day One

01

Observability is not optional

You can't debug what you can't see. Instrument everything from day one. CloudWatch, Dynatrace, Kibana — pick your stack and make it a first-class citizen, not an afterthought.

02

Boring upgrades are load-bearing

The Java 11 to 21 migration wasn't glamorous. Neither was the Spring Boot upgrade. But the systems that ran on top of them got faster, cheaper, and safer. The invisible work is often the most important.

03

Clarity is a technical skill

Whether you're writing a design doc, a Jira ticket, or a prompt to an AI tool — the ability to articulate a problem precisely is as valuable as any framework expertise. Invest in it.

04

Ownership changes everything

Writing code is easy. Owning a service — monitoring it, improving it, taking the 2am page — is where engineers grow. Seek ownership, even when it's uncomfortable.

05

The domain matters

Healthcare software is different from e-commerce software. Not just technically — the stakes are different, the culture is different, the meaning is different. Pay attention to where you're building, not just what.
